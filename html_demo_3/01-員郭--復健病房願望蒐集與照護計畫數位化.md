### 概覽

- 會議核心目標是討論一套前端願望蒐集介面（圖像化選單）與後端照護計畫、PAC系統及生活功能解鎖護照的串接路徑，並規劃在11月中旬前準備可展示的 Demo 材料與報告內容。  
- 討論重點包含資料結構（願望→短中長期目標→150 項細項映射）、使用情境（病人、護理師、治療師、家屬）、AI 協助自動產文的可能性，以及演示形式（錄影 Demo vs. Live demo）。

### 主要議題

### 前端願望蒐集介面設計（圖像化選單與展開機制）

- 背景：期望以圖像卡或大按鈕讓病人或照護者直覺選取願望，避免一開始就被量表文字淹沒；介面要能呈現大類（生活、運動、工作、娛樂、照護）並可展開小項目。  
- 關鍵觀點：多位參與者建議首頁不要顯示過多選項，採大類＋展開細項（最多顯示 6\~11 格）能降低病人選擇負擔；對於無法選擇或認知差的病人，建議由家屬或護理師代選並有暫存機制。  
- 結論：採「大類 → 展開小項 → 標記重複/重要性（例如星等或顏色）」的呈現方式，並保留「其它」可讓使用者手動輸入補充。  
- 未決與風險：如何設定每個大類與對應小項的數量（展開深度）、以及選項命中率低時的替代方案仍需細化；UI 在平板尺寸上的可用性需驗證。

### 後端映射與資料結構（願望到短中長期與150 項細項）

- 背景：目標是把病人的主觀願望，映射到可執行的照護計畫與 PAC 所需量表，並在出院時能產生結案成果。  
- 關鍵觀點：建議固定三層結構（短期 / 中期 / 長期），並用既有的 150 項細項作為底層任務庫；若願望不在既有庫內，可以用文字描述或錄音逐字稿補齊，並透過 AI 建議對應項目。  
- 結論：採「願望選取 → AI 或規則化映射到 150 項細項 → 生成短中長期任務」流程，並允許人為編輯與合併重複項目（以重複次數或星等標示優先順序）。  
- 未決與風險：要先準備好可供選取的卡牌（資料庫），否則 AI 與映射效果有限；資料量與品質不足會影響自動生成的可靠性。

### 與 PAC / 臨床量表的整合（工作流程與責任分工）

- 背景：PAC 系統已有既定的評估量表與出院流程，團隊希望新介面能與 PAC 串接或至少把結果回拋給 PAC。  
- 關鍵觀點：PAC 要求上端提交固定量表與照護計畫（文字），但前端的圖像化願望有助於團隊聚焦目標；護理師、專科護理師與治療師在流程中擔任不同角色，前端可由護理師先暫存、治療師後續核定或修改。  
- 結論：第一階段先獨立運作、產出願望與生成的短中長期文字（可匯出/回傳），再逐步以 Webhook 或 API 與 PAC 整合；出院時再將內容匯入生活功能解鎖護照作為結案成果。  
- 未決與風險：需釐清回傳 PAC 的欄位位置與格式（是獨立按鈕跳轉還是直接回寫），以及是否會增加治療師或護理師的工作負擔。

### AI 支援的自動化（由圖像到文字、由願望到任務）

- 背景：討論將 AI 用於自動產出短中長期目標文字、從錄音逐字稿擷取關鍵願望、以及依據選中的卡牌生成對應訓練項目的可行性。  
- 關鍵觀點：AI 可減少人工撰寫時間，但前提是要有足夠且品質良好的語料（常用片語、範本、150 項任務庫）；亦有人提醒 AI 不是魔法，人力流程先可行，再以 AI 才能放大效益。  
- 結論：短期以 AI 輔助生成草稿（供治療師修改）為主，並把常見的長期目標範本、片語、圖卡對應資料用於訓練；AI 功能逐步上線，避免一開始即把 AI 當核心功能。  
- 未決與風險：語言雜訊（中英夾雜、臺語）、會議錄音品質、與少量或特殊願望對 AI 的命中率，需透過資料清洗與人為監督降低錯誤。

### Demo 與報告準備（11月報告節點）

- 背景：團隊需在 11月中旬對上級（含院方或主管）展示進度，期望 Demo 穩定不出錯，錄影比 Live Demo 風險低。  
- 關鍵觀點：錄影 Demo（像日本參觀的側錄方式）能呈現操作情境且風險較低；若要 Live Demo，則需額外搭建可上線的 App/AI 後端，工程負擔大。  
- 結論：優先準備錄影式 Demo 與 UI 截圖，將流程與畫面固定並在會前演練；同時先做能獨立運作的第一階段功能，11月用示範影片說明整體概念。  
- 未決與風險：若要求現場互動，工程時間與資源不足會帶來展示風險；需決定影片長度與重點（建議 20\~30 分鐘口頭說明配短片）。

### 使用者角色與實務流程（誰做、何時做、如何暫存）

- 背景：流程涉及病人、家屬、護理師、專科護理師、治療師與醫師，且不同角色在不同時間點需要看到或編輯資料。  
- 關鍵觀點：病人可在平板上直觀點選願望，護理師可先填暫存、治療師稍晚審核並生成最終照護計畫；團隊會在例行會（每 3 週）回顧進度並調整訓練方案。  
- 結論：系統需支援暫存機制、權限控管（檢視與編輯）與病人專屬帳號檢視；並在後臺保留可供匯出報表與統計的功能。  
- 未決與風險：誰最終負責提交照護計畫仍需明確（討論傾向由團隊共同產出、治療師負責治療計畫），且過多表單可能增加臨床人員負擔。

### 其他技術與實務細節

- 要先建立卡牌/圖像庫與 150 項細項對照表供系統使用，並讓介面支援手動新增與編輯。  
- 會議中多次強調先做到「人可以做」的流程，再以 AI 幫忙減輕工作量；語音轉寫、逐字稿與常用片語需收集做為訓練素材。  
- 建議初期先以錄影 Demo、UI 截圖與樣板資料展示，後續再做 API 或 Webhook 與 PAC 串接。
